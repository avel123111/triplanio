# Triplanio: периодическая сверка энтайтлмента (TRIP-153)

Право на Pro живёт в ДВУХ местах: **реестр** (`subscription`, `purchase`) и **кэш**
(`users.subscription_status/end_date`, `trips.is_pro_trip`). Приложение читает кэш.
Ломается двумя способами: реестр разошёлся со Stripe (событие потерялось) или кэш
разошёлся с реестром (recompute не позвали).

## Зачем понадобилась (ленивая сверка не покрывает)

`needsEntitlementReconcile` (`_shared/reconcileEntitlement.ts`) при `status='pro'` и
будущей дате возвращает `false` — то есть **не запускается у того, чей кэш врёт В НАШУ
ПОЛЬЗУ**. И не запускается вовсе у того, кто не заходит: все вызыватели — `getUserPlan`
и `checkSubscriptionStatus`. `reconcileTripEntitlement` зовётся только под
`if (tripIsPro && …)`, то есть требует УЖЕ выданного права → «деньги взяли, право не
выдали» не лечится ничем.

## ★Живой дефект прода, найденный замером (2026-08-06)

Трип `49a1de05`: владелец `free`, трип не Pro, но `addons.telegram_assistant=true` и
ДВЕ живые привязки в `trip_telegram_integrations`. **`aiGate` Pro не проверяет вообще** —
он держится на инварианте «есть привязка ⇒ трип Pro» (записано в его шапке) и пускает
сообщение в Gemini по одному факту привязки. Механизм отката существует и корректен, но
зовётся ТОЛЬКО на запись вебхука, а **потеря Pro по времени записи не порождает** —
звать его было некому. Это же хоронит идею «триггер в БД вместо крона».

## ★★★РАЗГАДКА того трипа + подтверждённая дыра вебхука

Pavel: `dddyakonova` — ТЕСТОВЫЙ юзер. Фейковая подписка была вставлена в БД руками,
потом строка удалена; затем Pavel выпустил купон в Stripe и активировал подписку
**из дашборда**. Реальной оплаты не было → Stripe прислал только
`customer.subscription.created`.

**Это событие вебхук НЕ обрабатывает** (`switch` знает `checkout.session.completed`,
`invoice.paid/payment_failed/updated`, `customer.subscription.updated/deleted`,
`charge.refunded/dispute.created` — и всё). Хуже: `customer.subscription.updated`
работает **только `if (existing)`** (`stripe-webhook:377-378`), ветки «строки нет» нет
→ **из этого состояния вебхук не выберется НИКОГДА**, сколько бы событий по подписке
ни пришло. Подписка, заведённая мимо чекаута (дашборд, купон, админка), у нас не
материализуется в принципе. `invoice.paid` — единственная ветка с `else`-upsert'ом,
поэтому спасает только если по подписке когда-нибудь выставится инвойс.

★Прямое следствие для разрушающих чисток: бекфилл-скрипт снёс бы привязку у человека,
**который по Stripe имеет право**. Ровно тот исход, который предсказало ревью, —
подтверждён фактами, а не рассуждением.

★★И граница Сверки А: **её крон этот случай НЕ чинит**. Она сверяет кэш с РЕЕСТРОМ, а
реестр пуст → `recompute` даёт free, кэш уже free → расхождения нет. Чинит это только
Сверка Б (реестр против Stripe) либо ленивая сверка при заходе юзера в приложение
(ветка stuck-FREE, `listSubscriptionsByCustomer`). Крон при этом ПОКАЖЕТ её — под
классом `tg_binding_on_non_pro_trip`. Видимость и починка тут в разных PR, и это надо
проговаривать, иначе «крон же есть» читается как «починится само».

## ★★Почему чинить это разовой миграцией НЕЛЬЗЯ (поймано ревью, не тестом)

Первая редакция PR1 несла разовую миграцию «снести привязки на не-Pro трипах». Она
опиралась на `is_trip_pro` → `is_user_pro` → `users.subscription_status`, **то есть на
КЭШ — ровно на то, что и находится под подозрением**. Замер владельца того трипа
(`63782d4c`, dddyakonova@gmail.com):

- `provider_customer` = `cus_UwFCk5BMmrTfXj`, заведён 2026-07-23;
- строк в `subscription` — **0**, в `purchase` — **0**;
- `entitlement_synced_at` — **NULL** (ленивая сверка у неё не отработала НИ РАЗУ);
- три Pro-аддона включены, 2 живые привязки.

Это дословно сигнатура **stuck-FREE** («кэш не pro, но есть provider_customer =
потерянная активация»). Кто-то включил Pro-аддоны, а реестр пуст — ответ знает **только
Stripe**. Два исхода, оба плохие: снести интеграцию платящему клиенту (обратно
автоматически не вернётся — ни вебхук, ни сверка привязок не СОЗДАЮТ) либо уничтожить
единственную улику того, что Pro когда-то выдавали. **Миграция убрана из PR1**; вопрос
закрывает Сверка Б (Stripe), а до неё — ручная проверка customer'а в дашборде.

Мораль шире одного трипа: **разрушающее действие нельзя вешать на предикат, который сам
и является предметом сверки.**

Юзеров с `provider_customer` и `status<>'pro'` на проде четыре, но три объясняются без
Stripe: у одного строка подписки есть (`canceled` — кэш `free` корректен), у второго это
та самая сирота-покупка (трип удалён), третий — обезличенный удалённый аккаунт.
**Неизвестный ровно один** — `dddyakonova@gmail.com`. Считать «4 подозрительных» и
считать «1 подозрительный» — разница между «идём в Stripe четыре раза» и «один раз».

Там же: единственная покупка прода — сирота (`trip_id=NULL`, трип удалён, FK
`ON DELETE SET NULL`). Масштаб прода на тот момент: 38 юзеров, 2 pro, 4 строки
`subscription`, 1 `purchase`, 50 трипов, 13 `webhook_event` (0 failed).

## ★★Грабля, из-за которой находка молчала бы: `revoke_*_pro_addons` возвращает НЕ погашенное

В её `WHERE` четвёртая ветка `OR` — `exists (select 1 from trip_telegram_integrations
i where i.trip_id = t.id)`, а сам `UPDATE` трогает только `details.addons.*`. Значит
трип с живой привязкой и уже потушенными флагами **возвращается на каждом вызове,
вечно**: функция не идемпотентна по возвращаемому набору.

Отсюда два следствия, оба неочевидные:
- считать «погашено» по возвращённому набору нельзя — находка горела бы каждый час на
  уже починенном трипе;
- но считать по ФАКТИЧЕСКОМУ изменению флагов тоже недостаточно — тогда сломанный
  инвариант попадёт в журнал ровно ОДИН раз (в час, когда флаги флипнулись) и дальше
  замолчит, пока привязка жива. Поэтому стоячее состояние («живая привязка на не-Pro
  трипе») вынесено в ОТДЕЛЬНЫЙ report-only класс, считаемый запросом. Терминируется сам,
  когда `DELETE` уедет внутрь `revoke_*`.

## ★Предикат права: у `recompute_user_entitlement` ТРИ входа, не два

`status`, `current_period_end` **и** `provider_meta->>'next_payment_attempt' + 1 day`
для `past_due` (грейс, TRIP-158, детерминирован без `now()`-математики). Копия «по
описанию» рапортовала бы КАЖДОГО дённинг-юзера как расхождение ежечасно уровнем `error`.
В ТЗ это утверждение было неверным — поймано только чтением живого
`pg_get_functiondef`. Формула в новой миграции скопирована дословно и **пиньтся тестом**
(побайтовое сравнение с миграцией TRIP-158). `recompute_trip_entitlement` времени не
учитывает вовсе (lifetime), `is_user_pro` учитывает (`end_date > now()`).

## Устройство Сверки А (PR1)

Чистый SQL + `pg_cron`, ноль вызовов наружу, вебхук не тронут. **Ничего не вычисляет
сама** — зовёт `recompute_*` / `revoke_*` и журналирует разницу до/после; разница
одновременно и починка, и метрика. Проход ПОЛНЫЙ, без выборки кандидатов: выборка это
предикат, а промах предиката не краснеет — он молча не проверяет.

Режимы `report`/`apply`. **`report` откатывает свои записи подтранзакцией, но НЕ
переменные plpgsql** (они переживают откат) — поэтому «стало» остаётся посчитанным ТЕМ
ЖЕ кодом, что и в `apply`, и второй формулы держать не надо. Та же подтранзакция даёт
второе: сбой на одном юзере не роняет прогон, он становится находкой `action='failed'`.
Расписание введено В РЕЖИМЕ `report` намеренно; перевод на `apply` — отдельной
миграцией. Дефолт функции тоже `report`, чтобы голый вызов из SQL-редактора не оказался
массовой правкой прав.

Журнал — два уровня: `reconcile_run` (сводка) и `reconcile_finding` (построчный след).
⚠️**Соблазн сказать «висящий `status=running` = умер на полпути» — ЛОВУШКА**: `pg_cron`
зовёт функцию ОДНОЙ транзакцией, падение откатывает всё, включая саму строку прогона, —
такой строки не увидит никто. Крах Сверки А читается в `cron.job_run_details`; в журнале
отражается только ЧАСТИЧНЫЙ сбой (`status='partial'`, есть находки `action='failed'`).
Для Сверки Б через HTTP наоборот — `pg_net` асинхронен, там `running` реально повиснет.
Ярус B, RLS без политик + revoke; **вью тоже надо ревокать** (и ставить
`security_invoker`) — `ALTER DEFAULT
PRIVILEGES … GRANT ALL ON TABLES TO anon, authenticated` в baseline распространяется и
на вью, то есть новая вью рождается читаемой анонимом.

## ★Почему `recompute_*` научили не переписывать идентичное

Обе делали безусловный `UPDATE`. Полный почасовой проход превращает это в `UPDATE`
каждой строки `users` и `trips` ежечасно. Замерено перед правкой: ни `users`, ни `trips`
НЕ в публикации `supabase_realtime`, все их триггеры `ON INSERT` → рантайм не ломается,
цена только мёртвые кортежи. Правка нужна по смыслу, а не по срочности.

## Рельс и почему НЕ Vault

Прецедента `vault.decrypted_secrets` в репо НЕТ ни одного (проверено по всем миграциям).
Два существующих cron-джоба (`chat-ai-run-watchdog`, `tg-reminders-undelivered`) секрет
не хранят, а зашивают Sentry DSN в URL. Установленный приём для «внешний планировщик
дёргает edge» — **n8n + `requireN8nSecret` + строка `'n8n'` в `DOORS`**
(`getPendingReminders`, `aiGate`). Поэтому Сверка Б (PR3) идёт через n8n, а не через
`pg_cron`+`pg_net`+Vault. Цена принята: расписание живёт вне репо/ревью/CI, значит
удалённый воркфлоу невидим ничем, кроме сторожа (PR4).

## Sentry: алерт шлётся из SQL, environment зашит 'production'

Тот же ingest-DSN, что у `tg_reminders_undelivered_watchdog`. Окружение из SQL не
выводится (обе базы называются `postgres`) — РЕШЕНИЕ Pavel: зашить 'production' и
разбирать руками, потому что молчащая сверка бесполезна; находки с dev приедут с
меткой production, следствие принято. Уровень `error` по всем находкам («на старте
ничего не глушим»). ⚠️Сообщение события — КОНСТАНТА без чисел и id: постим сырым
POST в ingest без SDK, Sentry группирует по тексту, поэтому переменная в message
рожала бы новый issue каждый час; числа уходят в `extra`, группировка пинится явным
`fingerprint` (у edge-функций его нет — там группирует SDK).

## Гарды, которые тут срабатывают

- **2a** — таймстамп миграции: `mm==00 && ss==00` = «набрано руками», падает. Нужен
  `supabase migration new` (в этом окружении CLI нет — ставить правдоподобное время).
- **2g** — сырая `text`-колонка без кэпа. Домены `public.short_text` (300) /
  `long_text` (10000) / `url_text` (2048) снимают вопрос без file-level маркера
  `caps-guard: allow-uncapped` (тот глушит ВЕСЬ файл — тупой инструмент).
- **2e** — `TABLES` в `security-tiers.mjs` НЕ тотальна (STATIC итерирует по манифесту,
  новая таблица его не роняет), а **`DOORS` тотальна**: новая edge-функция без строки
  роняет сборку. То есть 2e покраснеет на PR3, а не на PR1.
- **2b** ловит только DDL (`DROP COLUMN/TABLE/NOT NULL/RENAME/ALTER…DROP`) — **`DELETE
  FROM` он не видит**, безопасность разовой чистки данных держится на ревью, не на гарде.

## Грабли окружения

В ворктри нет ни `postgres`, ни `docker`, ни `node_modules` → поведенческие тесты SQL и
`eslint` локально невозможны, первый живой прогон = деплой в dev через CI (ещё одна
причина вводить расписание в `report`). `audit-design.test.mjs` даёт **0 pass на чистом
`origin/dev`**, `check-css-semantics` / `check-design-floor` падают 12/33 там же — чужая
краснота, сверять с базой отдельной ворктри, а не считать своей.
