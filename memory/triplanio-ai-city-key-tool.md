# Идентичность города от ИИ: инструмент справочника и ключ (TRIP-524)

## Зачем это есть

Пока город приезжает от модели ТЕКСТОМ, промах возможен всегда, и он бывает двух
видов: (а) города с таким именем у нас нет — узел встаёт без координат и таймзоны
и краснеет на шаге 2; (б) имя есть, но не то — резолвер взял тёзку. Жёсткий скоуп
по стране (TRIP-159) вероятность сдвинул сильно, но класс жив: в справочнике 622
пары «одно имя, одна страна», и пять Портлендов в США — как раз такая.

★ КОРЕНЬ, КОТОРЫЙ НЕ ЛЕЧИТСЯ РАНЖИРОВАНИЕМ: резолвер видит ОДНО имя и страну,
маршрута он не видит по построению. «Портленд» + `US` он ранжирует по населению и
отдаёт Орегон — и это правильный ответ на тот вопрос, который ему задали. У модели
контекст есть («Новая Англия», соседние города, координаты), поэтому выбор отдан
ей, а идентичность переведена с имени на КЛЮЧ `geonameid`.

## Как работает сейчас

**Инструмент агента** — edge `gazetteerSearch` (`verify_jwt = false`, дверь
`requireN8nSecret`, ярус манифеста `n8n`). Принимает `{cities: [{city_name,
city_name_en?, country_code?}], language?, limit?}`, отдаёт `results` — по элементу
на каждый ЗАПРОШЕННЫЙ город В ТОМ ЖЕ ПОРЯДКЕ, у каждого `candidates` с
`geonameid`, `city_name`, `region` («регион, страна»), `country_code`,
`population`, `latitude`, `longitude`.

- Имена полей — из словаря МОДЕЛИ (`OPS` в `src/pages/create/aiOps.js`), а не из
  словаря RPC (`q`/`q_en`/`cc`/`display`/`subtitle`). Иначе у модели два словаря
  на одну сущность — ровно то, из-за чего она путала `date` и `startDate`.
- Ранжирования в функции НЕТ: она зовёт тот же `search_gazetteer_batch` с тем же
  payload, что фронт (`buildResolvePayload`), разница ровно в `lim` (агенту нужны
  кандидаты, резолверу фронта — один лучший). Иначе агент выбирал бы из одной
  выдачи, а фронт проверял по другой.
- Выравнивание по входу — ПО ПОСТРОЕНИЮ: ответ строится из входного списка, строки
  лишь раскладываются по позициям `ord`. Пустой `candidates` = города нет.
- Своего rate-limit нет намеренно: постучаться сюда нельзя иначе как в ходе
  обработки реплики, а на реплики лимит уже стоит (`planTripWithAi`, 50/час).

**n8n** — воркфлоу `AI Trip Planner v2` (`mnLYKZCMpvepHwag`): нода `Gen env`
(Data Table `environments` → `backend_url` по метке `body.env`), инструмент
`findCity` (HTTP Request Tool, Bearer-креденшел «Bearer Auth account»), правило в
системном промпте («найди город инструментом и верни `geonameid` выбранного»,
один вызов на все города хода, потолок 3 обращения), схема Structured Output
Parser перегенерирована `opsJsonSchema()` — источник словаря один, копия
производная.

**Ключ в операциях** — `geonameid` у города операции НЕОБЯЗАТЕЛЕН (тип словаря
`id`). Без инструмента город приезжает одними именами и резолвится поиском ровно
как раньше: совместимость в обе стороны (старый фронт лишнее поле игнорирует,
новый работает без него).

⚠️ ФРОНТОВАЯ ПОЛОВИНА (дверь `citiesByIds` → RPC `gaz_by_ids`, разбор запроса и
запасного города в `aiOps`) — в PR #1197, в `dev` ещё не влита. ОТКРЫТО: та же
работа может быть сделана БЕЗ второй клиентской двери — полем `id` в элементах
существующего `search_gazetteer_batch`; тогда клиентских RPC газеттира остаётся 3
и цель гарда 2r не трогается. Решение за Pavel.

## Правила, за которые заплачено

**Замер инструмента требует контроля, который меняет И ПРОМПТ.** Первая попытка:
нода `findCity` отключена, промпт прежний («зови инструмент») — модель ждала
ответа, не дожидалась и возвращала ПУСТОЙ маршрут с текстом «Searching for
Portland and Boston in the database…». Числа того захода (медиана 11.51 с, разброс
2–20 с) — мусор. Годный контроль = дореформенный промпт + отключённая нода.

**Инструмент стоит один круг модели, а не только сеть.** Контроль на той же машине
в тот же час, 4 промпта × 2 прогона: медиана 11.37 → 13.62 с (**+2.25 с, +20 %**),
медиана попарных дельт +2.43 с. Сам запрос в справочник — 1.6 с; остальное модель
думает второй раз. На 2 городах дельта в шуме (−0.8 с), на 4 городах +1…+4 с, а
при повторном поиске (город не нашёлся с первого написания) кругов два: +4.6 с.

**Правила «не отчитывайся о процессе» и «если инструмент не ответил — всё равно
построй маршрут» ОТНЯЛИ вызов инструмента** (на двух прогонах модель перестала его
звать). Сняты. Промпт агента правится по одному правилу за раз и с прогоном после.

**Сбой инструмента деградирует корректно, костыля не нужно.** Проверено подменой
URL на несуществующую функцию: модель получила 404, построила маршрут БЕЗ
`geonameid`, сбой не упомянула, ход 9.7 с. Пустой ответ бывает только при
ОТКЛЮЧЁННОЙ ноде — искусственная ситуация, в проде её нет.

**`backend_url` в Data Table лежит СО СЛЭШЕМ на конце.** Соседние воркфлоу живут с
`…supabase.co//functions/v1/…` годами, но один прогон получил на живую функцию
`404 NOT_FOUND` (тот же адрес из curl отвечал 401, т.е. функция была на месте).
В `findCity` слэш нормализуется выражением.

**`revoke ... from public` после `create function` — NO-OP.** Supabase раздаёт
EXECUTE новым функциям схемы `public` НАПРЯМУЮ ролям `anon`/`authenticated` через
`ALTER DEFAULT PRIVILEGES`. Третий раз одни грабли: TRIP-49, TRIP-226
(`gaz_project`), TRIP-524 (`gaz_by_ids`, уронил деплой dev на LIVE-страже ярусов).
Идиома: `revoke all on function <f> from public, anon, authenticated;` затем
`grant execute` нужной роли. STATIC-половина гарда 2e этого не видит по
построению — LIVE гоняется только пост-деплой.

**Дрейф репо ↔ n8n машинно не проверяется** (воркфлоу не версионируется в git).
Схема парсера и строки промпта — производные от `aiOps.js`; связь держится
соглашением. Гард — в Ф4 эпика.

## Масштаб проблемы на сегодня (прод, замер до кода)

299 сохранённых визитов, 113 уникальных городов. Без `geonameid` — 1 из 299 (за
последние 30 дней 0). Городов с тёзкой в той же стране — 0 из 113. То есть сегодня
проблема не горит: инструмент оправдан как обкатка механизма перед Ф6 и страховка
на рост, а не как тушение пожара.
