**PR со статусом `merged` доказывает только одно: он влился в СВОЮ базу.** Если база — не `dev`, а другая ветка, код в `dev` может не попасть, и никто об этом не скажет.

**Случай (TRIP-340 → TRIP-362, 2026-08-06/07).** Подзадача поставлялась цепочкой PR со ступенчатой базой: `PR2 (витрина) → ветка PR1 → dev`. Оба PR смёржены, оба честно помечены `merged`:

```
#693 (ветка PR1 → dev)   merge-commit 6a45da3   14:57:35 +0200
#694 (витрина → ветка PR1)                      14:57:37 +0200
```

**Две секунды.** Ветку PR1 слили в `dev` первой, витрина приехала в неё второй — и осталась там навсегда: `dev` уже забрал снимок ветки ДО неё. Через сутки в `dev` не было ни `src/pages/Kit.jsx` (421 строка), ни 24 строк роутинга, ни роута `/kit`. Коммит при этом цел и достижим — `6821d41` в `refs/pull/694/head`, чинится черри-пиком в отдельный PR **с базой `dev`**.

Опаснее всего то, что **все индикаторы зелёные и все они не врут**: Linear показывает Done, GitHub показывает merged, ревью пройдено, CI зелёный. Ни один из них не отвечает на вопрос «а в `dev` это есть». Обычный гейт из [[feedback-new-commits-need-new-pr-after-merge]] тут тоже молчит: там ловится сирота-коммит БЕЗ PR, а здесь PR есть, он открыт был, отревьюен и закрыт мёрджем — просто не туда.

**Почему это класс, а не разовая неудача.** Ступенчатая база выбирается ради чистого диффа («в PR2 видна только витрина, а не PR1 целиком») — то есть ради правильной цели. Гонка возникает от того, что `dev` и промежуточная ветка мёржатся независимо, и порядок не гарантирован ничем: достаточно, чтобы внешний мёрдж случился раньше внутреннего. Чем короче интервал между мёрджами, тем незаметнее потеря.

**Побочная цена.** Вместе с экраном в `dev` не доехали его находки, зафиксированные ТОЛЬКО в теле PR (тело PR — не репозиторий): что `Skeleton` и `RoleBadge` не имеют ни одного CSS-класса и потому невидимы каталогу и гардам 2m/2n/2o; что ступени `.row--g1`, `.col--g2`, `.grid--g1`, `.grid--g5` не объявлены и молча дают отступ по умолчанию; что обход `document.styleSheets` был написан неверно и **выглядел работающим**. Знание, живущее только в описании PR, теряется вместе с поставкой.

**Why:** «смержен» — свойство PR, а не репозитория. Вопрос, который на самом деле задают («поставка доехала?»), проверяется только состоянием `dev`, и проверка стоит одну команду. Пропуск этой проверки закрывает задачу как Done при пустом `dev` — то есть ломает не только поставку, но и учёт: следующая фаза строится на том, чего нет.

**How to apply:**

1. **По умолчанию база PR = `dev`.** Ступенчатая база (`PR2 → PR1 → dev`) — осознанное исключение ради читаемого диффа, и оно ОБЯЗЫВАЕТ к пункту 2. Если можно не городить цепочку — не городи.
2. **После мёрджа ЛЮБОГО PR проверь `dev` по файлу, который этот PR добавлял** — не по статусу PR:
   ```
   git fetch origin dev
   git ls-tree -r origin/dev --name-only | grep <файл>
   git merge-base --is-ancestor <sha> origin/dev && echo "в dev" || echo "НЕ В DEV"
   ```
   Проверять по **файлу или SHA**, а не по названию ветки: squash-мердж не сохраняет SHA исходных коммитов, поэтому у squash-веток работает только проверка по файлу/содержимому.
3. **Мёржить цепочку СНИЗУ ВВЕРХ и по одному:** сначала `PR2 → PR1`, дождаться, что ветка PR1 действительно содержит витрину, и только потом `PR1 → dev`. Обратный порядок — это и есть описанная гонка.
4. **Не оставляй знание только в теле PR.** Находки, ради которых заводился экран/гард, переноси в `memory/` или в шапку файла: тело PR не переживает потерю поставки и не читается следующей сессией.
5. **Восстановление — черри-пик в отдельный PR с базой `dev`, без правок кода** (он уже отревьюен). Но цену по гардам **перепроверить своим прогоном**: база уехала, а `floor-exempt`/`prefix-exempt` читаются из ДОБАВЛЕННЫХ строк диффа и действуют ровно один PR — маркеры надо выписывать заново, и с прошлого раза мог появиться новый гард (тут — 2p), которого в исходном PR не проверяли вовсе.
