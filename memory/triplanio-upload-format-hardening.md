## Где принимаются файлы (5 поверхностей, все через 2 бакета)

| Поверхность | Файл | Бакет |
|---|---|---|
| Аватар | `ScreenAccount.jsx` | `avatars` (**публичный**) |
| Документы трипа | `DocsLens.jsx` | `trips` |
| Вложения события И сервисов (eSIM/страховка) | `DocumentsField.jsx` — ОДИН компонент на 6 мест | `trips` |
| Встроенная загрузка в карточке события | `useEntityDocs` (`EventViewBody.jsx`) | `trips` |
| Распознавание брони | `EventAiBlock.jsx` | `trips` |
| Обложка трипа | `TripCoverPicker.jsx` | `trips` |

Документы **сервисов** лежат не в колонке, а внутри `trip_services.details.documents`
(`getDetailsDocuments`); у остальных — jsonb-колонка `documents`. Единая точка чтения на
показе — `useEntityDocs`, она обслуживает все 4 вида (отель/переезд/активность/сервис).

## Несущие факты

1. **`accept=` в разметке НЕ является проверкой.** Это подсказка диалогу выбора файла;
   drag-and-drop и прямой запрос её минуют. **Единственный неотменяемый гейт формата —
   `storage.buckets.allowed_mime_types`.** До TRIP-281 у `trips` он был `null` (любой тип,
   52 МБ при обещанных в UI 4–10 МБ), у `avatars` включал `image/svg+xml`. Доказательство,
   что фильтра не было: в прод-бакете лежали 3 объекта `text/html`. У `DocumentsField`
   дефолт был `accept='*'`.

2. **React 18 НЕ блокирует `javascript:` в `href`.** Проверено по исходнику: `sanitizeURL`
   — это dev-only варнинг, в прод-сборке проверки нет вообще (блокировка появилась только
   в React 19). CSP приложения (`vercel.json`) — только `frame-ancestors 'none'`, без
   `script-src`, то есть тоже не смягчает. **Не полагаться на React как на санитайзер.**

3. Отсюда была дыра на **угон аккаунта, для которого файл не нужен**: ссылка на документ
   пишется фронтом напрямую (RLS `_can_edit_trip AND created_by = auth.uid()`), в БД стоял
   только кэп длины 2048 (TRIP-169) → писался `javascript:…` под именем «Билет.pdf».
   Клик другого участника → код на triplanio.com, где `persistSession: true` держит в
   localStorage **refresh**-токен (не пароль): угон переживает смену пароля, рвётся только
   принудительным отзывом сессий. Живые данные были чисты (0 кривых ссылок), эксплуатации не было.

4. **Ссылка на документ живёт в jsonb-массиве `documents`, а НЕ в колонке.** Плоские
   `trip_documents.file_url`/`file_name` были МЁРТВЫМИ (100% NULL в проде и dev за всю историю,
   ни одного писателя: `insertTripDocument` их не кладёт, UPDATE-пути у таблицы нет, ни одна
   функция БД их не трогает) и **дропнуты** в TRIP-281. Ловушка: первая попытка навесить
   `CHECK` пошла именно на колонку — констрейнт на мёртвом поле ВЫГЛЯДИТ покрытием, не будучи им.
   Перед тем как защищать поле, проверь, кто в него пишет и рендерится ли оно.

5. **`normalizeExternalUrl` (`booking-platforms.js`) обезвреживает чужую схему** — всё, что
   не `http(s)`, получает `https://` ПРЕФИКСОМ (`javascript:x` → `https://javascript:x` —
   вообще невалидный URL, браузер никуда не идёт). Устойчиво и к `java\nscript:` (перенос
   строки браузер режет уже ПОСЛЕ того, как строка стала https). На этом держатся все `href`
   из БД-полей. Инвариант закреплён тестом `booking-platforms.test.js`, а не только
   комментарием: «научить» её пропускать URL с уже имеющейся схемой = молча вернуть XSS.

6. **`contentType` в `supabase.storage.upload()` для `File`/`Blob` ИГНОРИРУЕТСЯ.** storage-js
   шлёт multipart, тип части ставит браузер из `file.type`; опция применяется только к
   не-Blob телу (проверено по исходнику `uploadOrUpdate`). Единственный способ задать тип —
   пересобрать файл: `new File([file], file.name, { type })`.

7. **MIME-таблица ОС разная на разных машинах**, а клиентский список — по РАСШИРЕНИЯМ, поэтому
   два списка неизбежно расходятся: где не зарегистрирован Excel, `.csv` приезжает как
   `text/plain` и бакет его отбивает сырой ошибкой (нашёл ревьюер Codex на PR 620). Поэтому
   `uploadTripFiles` пересобирает файл с типом ПО РАСШИРЕНИЮ (`uploadContentType`) — расхождение
   класса закрыто целиком, а не одним значением, и `text/plain` в белый список НЕ добавлен
   (это единственный тип, который браузеры исторически досниффивали до HTML).
   Побочно чинит превью: `.pdf`, приехавший как octet-stream, теперь хранится как PDF.
   `application/octet-stream` в списке остаётся — три поверхности грузят в обход шва
   (парсер брони, обложка, аватар); это безопасно (браузер его всегда скачивает, а в `<img>`
   определяет формат по байтам).

## Как теперь

Граница белого списка — **«браузер это ИСПОЛНЯЕТ»**: исключены только HTML и SVG. Офисные
`.doc/.xls` ОСТАВЛЕНЫ осознанно — браузер их не исполняет (макросу нужен настольный Office
и явное «разрешить содержимое»), а турагентства их реально присылают; запрет ломал бы живой
сценарий без выигрыша. Словарь форматов один на всё — `src/lib/fileType.js`: ОДНА карта
расширение→MIME, из неё выведены и списки расширений, и `accept`, и `uploadContentType`,
поэтому «разрешено» и «чем является» разойтись не могут. Тест `fileType.test.js` ЧИТАЕТ
белый список прямо из файла миграции (а не хранит копию) — иначе проверка «ничего
исполняемого» была бы кольцевой; при будущем схлопывании миграций в baseline тест громко
падает на пустом списке, путь надо перенацелить.

**Проверки формата И размера стоят в ШВЕ `uploadTripFiles` (`documentMutations.js`), а не на
экранах**: все три документные поверхности идут через него, поэтому один гейт закрывает все и
новый вызывающий не может его забыть. Ошибки возвращаются как `reason:'format'|'size'` в
существующем контракте `errors`, текст для всех один — `uploadErrorText(error, t)` из того же
модуля. Свои проверки остались только у трёх поверхностей с ДРУГИМ лимитом (`EventAiBlock` 5 МБ,
`TripCoverPicker` 4 МБ, аватар 5 МБ) — это осознанные ограничения под задачу, не копипаста.

Цифра 10 живёт в ОДНОМ месте — `MAX_UPLOAD_MB`; её же читает подсказка `doc.upload_formats`,
так что обещание в интерфейсе и проверка не могут разойтись. Проп `maxFileSizeMb` у
`DocumentsField` удалён — его не передавал ни один из шести вызывающих.

Слой в БД: `CHECK` на схему в jsonb `documents` пяти хранилищ (`trip_documents`, `hotel_stays`,
`transfers`, `activities` + `trip_services.details`) через нативный `jsonb_path_exists`
(`$[*].file_url ? (!(@ like_regex "^https?://" flag "i"))`) — подзапрос в CHECK запрещён, а он
IMMUTABLE и работает выражением, поэтому своя функция не нужна. Констрейнты ВАЛИДНЫЕ (нарушений
0 в обеих базах). Плюс `td_link_url_scheme` на колонке `link_url` (она живая).

`booking_url` СОЗНАТЕЛЬНО без такого CHECK: в проде 17 живых строк со ссылкой без схемы
(15 отелей + 2 переезда) — констрейнт положил бы их, а `normalizeExternalUrl` их штатно дочиняет.

`parseBookingWithAi` принимает только URL нашего storage-origin: они уходят в ноду Mistral
OCR (`inputType: url`), которая скачивает что дадут. Фетчит Mistral со своей стороны, поэтому
во внутреннюю сеть это не вело, но платили бы мы.

Черновые обложки — `_drafts/<userId>/…` (`draftStoragePath`); раньше весь префикс `_drafts/`
был общим для всех авторизованных (чужой черновик читался и удалялся). **Сборки мусора у
`_drafts/` НЕТ** — комментарий, обещавший age-based sweep, описывал несуществующий механизм.
Ключ теперь пер-юзерный, поэтому будущая чистка обязана быть СЕРВЕРНОЙ (`service_role`):
клиент чужой черновик удалить не может.

Размеры: сервер `trips` 10 МБ (было 52), `avatars` 5 МБ.

**Одинаковое действие с разных экранов обязано вести себя одинаково.** Прикрепить файл к отелю
можно из формы редактирования (`DocumentsField` в `EventEditDialog`, 6 мест) и из просмотра
карточки (`useEntityDocs` → `EventModal` + `EventSourcePanel`) — для пользователя это один и тот
же ваучер у того же отеля, но это были два разных куска кода. До TRIP-281 они расходились: два
экрана отбивали ВСЮ пачку из-за одного плохого файла, третий (`DocsLens`) грузил остальные, и
тексты ошибок были три разных, два из них без имени файла. Теперь оба гейта в шве → поведение
одно: плохой файл стоит только себя, остальные грузятся, в ошибке всегда есть имя.

## Грабли этой задачи

**Валидный CHECK на пользовательский ввод = ставка на то, что мой снимок данных верен В МОМЕНТ
ДЕПЛОЯ, а не в момент написания.** Деплой TRIP-281 в dev упал (23514) на `td_link_url_scheme`:
я проверил нарушения `link_url` на ПРОДЕ и не проверил в DEV, а там лежали 7 строк вида «укпукп»
— мусор, записанный ДО того, как TRIP-230 поставил `normalizeExternalUrl` на запись. В комментарии
миграции при этом стояло «в обеих базах нарушений 0» — я это написал, не проверив.
Два вывода: (1) сверять КАЖДЫЙ констрейнт по КАЖДОЙ базе, dev грязнее прода — там тестовый мусор;
(2) для колонок со СВОБОДНЫМ вводом миграция должна быть самолечащейся — сначала `UPDATE`,
приводящий данные к инварианту тем же правилом, что и живой писатель, потом констрейнт. Тогда она
не зависит от снимка вообще. Для машинно-генерируемых значений (подписанные URL в `documents`)
наоборот — валидный констрейнт без апдейта, там нарушение = признак атаки и падать надо громко.
**Полезное:** упавшая миграция откатывается ЦЕЛИКОМ и в журнал НЕ попадает (проверено: `db push`
крутит файл в транзакции) → чинится тем же файлом, новый таймстамп НЕ нужен; но проверять журнал
обеих баз перед правкой обязательно.

**`collectDocPaths(documents, fileUrl)` — второй параметр использовали НЕ только документы.**
При выпиле мёртвой колонки я снёс его по грепу `file_url` и пропустил три вызова вида
`collectDocPaths([], coverUrl)` (`SettingsLens`, `TripCoverPicker`) — в них строки `file_url`
нет, поэтому греп по имени поля их не видит. Итог был бы тихий: подмена обложки перестала бы
подметать старый объект. Поймал `code-simplifier`. Правило: **при смене сигнатуры грепать имя
ФУНКЦИИ, а не имя поля.** Обложка теперь передаётся как `collectDocPaths([{ file_url: url }])`.

## Перезапись в user-write бакете: уникальный ключ, НЕ upsert (TRIP-367)

**Публичный бакет = ноль SELECT-политик (инвариант TRIP-48, гард 2e
`check-security-tiers`).** Поэтому для перезаписи файла НЕ использовать
`upsert:true`: supabase-js шлёт его как `INSERT … ON CONFLICT (bucket_id,name)
DO UPDATE`, а `ON CONFLICT DO UPDATE` под RLS обязан ПРОЧИТАТЬ конфликтующую
строку → без SELECT-политики Postgres отклоняет команду с `new row violates
row-level security policy` (403), причём плоский INSERT (нет конфликта) проходит
— баг всплывал только на ПЕРЕЗАПИСИ. Так и сломалась смена аватара: `avatars`
писался фиксированным ключом (`<uid>/avatar`) с `upsert:true`, а bucket-wide
`avatars_select` из baseline (которая удовлетворяла тот SELECT) сняла TRIP-48
(`20260713120000`, 2026-07-13) вместе с листингом → перезапись стала падать
(последняя успешная 10.07, за 3 дня до дропа).

**Правильный паттерн (как обложки трипа и официальный Supabase-пример
аватаров):** уникальный ключ на версию (`<uid>/<uuid>`, папка `<uid>/`
обязательна для owner-scoped `avatars_insert`) + указатель в профиле + best-effort
снос старого объекта (`parseStorageObjectUrl(prevUrl)` → `.remove([path])`).
Плоский INSERT в новый ключ конфликта не даёт → SELECT-политика не нужна;
уникальный ключ сам бьёт кэш, поэтому `?t=` не нужен. Промежуточный фикс
`20260818194500` (owner-scoped `avatars_select`) был откачен `20260818210000`,
т.к. любая SELECT-политика на публичном бакете валит гард 2e. `support`-бакет
уже так и делает (uuid-путь, без `upsert`). Наблюдаемость сбоя загрузки —
отдельно, [TRIP-284].

## Осознанно НЕ сделано

`Content-Disposition: attachment` на документах: после белого списка исполняемых форматов в
хранилище не остаётся, а PDF (самый частый документ, 53 в проде) перестал бы открываться
превью. Цена без выигрыша.

Prompt injection через содержимое брони — риск принят: у обоих AI Agent в воркфлоу
«AI Trip Parser» подключены только модель и output parser, **инструментов нет**, выход загнан
в схему, поля подтверждает пользователь. Максимум — правдоподобно неверная дата.

Ключ `doc.bad_format` заведён в Tolgee — иначе pull-on-deploy стёр бы его
([[feedback-new-i18n-keys-go-to-tolgee]]). Смежное: [[triplanio-security-tiers-architecture]],
[[triplanio-input-integrity-db-layer]].
