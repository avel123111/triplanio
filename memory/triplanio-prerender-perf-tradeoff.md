# Выпечка публичных страниц: чем она платит за содержимое (TRIP-520)

Факт, который стоил трёх дней спора и который нельзя выводить заново каждой
сессией.

## Что мерили

Одна машина, один коммит, две сборки — с выпечкой и `SKIP_PRERENDER=1`
(«то же приложение без выпечки», то есть поведение прода до TRIP-520).
Стенд — `npm run perf:lh -- --vs=SKIP_PRERENDER=1` (brotli, ETag/304, прод-заголовки,
мобильный пресет Lighthouse — тот же, что у PageSpeed), медиана 3 прогонов.

| | score | FCP | LCP | TBT | LCP-элемент |
|---|---|---|---|---|---|
| без выпечки | **86** | 2.70 с | 3.60 с | 27 мс | текст баннера согласия |
| с выпечкой | **67** | 3.36 с | 6.62 с | 171 мс | `div.hero-fill` (фото героя) |

Реальный троттлинг (4x CPU, 1.6 Мбит, DPR 2.625), та же пара сборок:

| | заголовок и текст лендинга видны |
|---|---|
| без выпечки | **8.0 с** |
| с выпечкой | **3.6 с** |

## Что это значит

**Выпечка отдаёт человеку весь текст на 4.4 секунды раньше и при этом теряет
~19 пунктов балла Lighthouse.** Противоречия нет: у сборки без выпечки в момент
замера на экране заставка и баннер согласия, поэтому её LCP — маленький
текстовый узел, а фотография героя в метрику вообще не попадает. Как только
страница начинает показывать настоящее содержимое, LCP-элементом становится
самый большой видимый объект — фотография, — и метрика считает время её
докачки.

Отсюда правило: **по одному баллу Lighthouse решение об этих страницах не
принимается.** Балл здесь мерит не то, ради чего задача делалась.

## Что проверено и НЕ помогает (не повторять)

Все три — замер на честном стенде, медиана 3 прогонов, разница в пределах шума:

- **`preload as=image fetchpriority=high` на кадр героя** — 0 (Lighthouse
  советует, аудит `prioritize-lcp-image` горит). Фазы LCP показывают
  `Load Delay 0 · Load Time 0`: о картинке узнают вовремя, узкое место не в
  обнаружении.
- **Снятие `preload` кириллического лица** на английской и испанской страницах
  (22 КБ) — LCP не двигает.
- **Пережатие кадра @2x** — на качестве 0.5 файл 2000 px весит 187 КБ вместо
  302 КБ при отличии 2.96 из 255: половина веса не уходит, вес задаёт
  разрешение, а не качество.

## Что помогло

**Мобильный кадр героя одним файлом вместо `image-set(1x, 2x)`** — LCP −0.95 с.
Телефон берёт вариант по ПЛОТНОСТИ ЭКРАНА, а не по размеру кадра, поэтому «2x»
доставался практически всем (у профиля Moto G Power, на котором мерит PageSpeed,
плотность 2.625): «104 КБ и 302 КБ» на деле означало 302 КБ почти каждому.
Цена глазами — 3.83 из 255 при выводе в реальный мобильный кадр; шаг 3x→2x,
принятый раньше, стоил 2.5, пересохранение файла тем же кодеком — 1.35.
Отменяет решение «верхний вариант — 2x» (Pavel, 06.09.2026).

## Ловушки замера

- **Стенд без сжатия врёт в разы.** `scripts/build/_serve.mjs` отдаёт байты как
  есть: `site.css` локально 113 КБ против 26 КБ на проде. Замер на нём давал
  выводы, ПРОТИВОПОЛОЖНЫЕ проду, — именно это заставило прошлую сессию
  перестать мерить локально и спорить по одиночным прогонам PSI. Мерить только
  `perf:lh` (у него brotli q11 и 304).
- **Один прогон PSI ничего не значит.** Три отчёта по одной и той же сборке
  превью дали 49, 54 и 69 (TBT 970 против 30). Дельта снимается только двумя
  сборками на одной машине в одном прогоне.
- **Speed Index под симуляцией Lantern вырождается в FCP** и разницу «спиннер
  против текста» не показывает — в стенде его нет намеренно.
- **Фазы LCP у CSS-фона неинформативны**: Lighthouse не сопоставляет
  `background-image` из переменной с ресурсом и пишет `Load Delay 0 · Load
  Time 0 · Render Delay <всё>`. Реальный вклад докачки виден только прогоном с
  настоящим троттлингом.
