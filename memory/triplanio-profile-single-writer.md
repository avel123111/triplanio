# Профиль: один кэш — одна дверь записи (TRIP-520)

## Как работает сейчас
- Кэш профиля на клиенте — `user` в `src/lib/AuthContext.jsx`. Читает его `getMe` (`select('*')`).
- **Единственная дверь записи — `updateProfile(patch)` там же.** Зовёт шов `account/profile` (upsert по актору, `_shared/resources/account.ts`), на успехе кладёт в `user` поле `row` ответа — полную обновлённую строку `users` той же формы, что отдаёт `getMe`. Сверка по ОТВЕТУ сервера (как `reconcileBookingWrite`), не второй круг и не догадка. Отказ возвращается `{error, code}` (TRIP-400), показ решает вызыватель.
- Вызыватели: `ScreenAccount` (имя, аватар загрузить/убрать) и `I18nContext.persistProfile` (язык, единицы). `checkUserAuth` после записи профиля больше не зовут — он остаётся для состояния, что меняется мимо клиента (вебхук Stripe → право).
- Язык = `routeLocale ?? profileLang ?? visitor` (три слоя, `I18nContext`). `setLang` пишет ТОЛЬКО два нижних слоя (localStorage + профиль); слой профиля становится живым потому, что запись идёт через владельца кэша. Отдельного «применить язык» нет намеренно.
- Гейт: `src/lib/profileWriter.test.js` — во всём `src/` шов `account/profile` зовёт ровно один файл, и дверь кладёт `data.row` в `user` без перечитывания.

## Ловушка (прод-баг 06–07.09.2026, PR #1171 → #1185)
Один кэш и N писателей, каждый из которых «должен помнить» перечитать — та же болезнь «три писателя», что TRIP-520 лечил для языка, уровнем ниже. Четвёртый писатель (`persistProfile`) не помнил → `user.language` стух → слой профиля перекрывал только что выбранный язык до перезагрузки. Ломалось ровно в сочетании «залогинен + в приложении» (на лендинге побеждает слой маршрута, у анонима слоя профиля нет), поэтому ручная проверка лендинга не ловила. Чинить надо не писателя, а число дверей.
