# Triplanio: храповик покрытия типами — гард 2s (TRIP-377)

★Ф0.1 эпика TRIP-374 («единая дверь в данные»), продуктового кода не тронуто ни
строки: `scripts/ci/check-ts-check.mjs` + 27 тестов + шаг 2s в джобе `guards`
(стандартная библиотека + git, инвариант «без `npm ci`» цел) + снятие фантома
`src/Layout.jsx` из `include` в `jsconfig.json`.

## Зачем отдельный гард, если есть `npm run typecheck`

`checkJs` в проекте ВЫКЛЮЧЕН, поэтому единственный вход в настоящую проверку
типов — построчная прагма `// @ts-check` в шапке файла. Прагму снимает одна
строка, и **`npm run typecheck` от этого ЗЕЛЕНЕЕТ** (ошибок стало не меньше, а
ноль), то есть регресс покрытия выглядит как успех и не виден больше ниоткуда:
ни lint, ни build, ни один из 18 остальных гардов файлов не читает под этим
углом. Это и есть предмет 2s — **единственный храповик джобы `guards`, идущий
ВВЕРХ**.

## ★★ Предикат раньше числа: 22 / 10 / 9 на одном дереве

«Файл с `@ts-check`» тремя способами даёт три разных числа, и никто не
ошибается — вопрос просто не был определён (тот же закон, что «сырой отступ»
962/1011/1304 и «163 токена двумя путями»):

* греп по тексту — **22**;
* греп + любой ведущий комментарий — **10**;
* СЕМАНТИКА TS (что реально проверяется) — **9**.

Разница не хвостовая: **12 файлов лишь УПОМИНАЮТ** `// @ts-check` в прозе
комментария (`AppHeader.jsx`, `icons.jsx`, `resolveAuthor.js`, `CityRow.jsx`,

комментарии, который TS прагмой не считает вовсе. Считать текстом значило бы
захраповить число, у которого 13 единиц ничего не проверяют, И ОДНОВРЕМЕННО
пропустить настоящий регресс: **сдвинь живую прагму под первый импорт —
проверка выключена, текстовое число не шелохнулось**. Родня «понижения метрики
инлайнов без снятия инлайна» (TRIP-388 PR 4): предикат, чувствительный к ФОРМЕ
ЗАПИСИ, — дыра по построению.

Постановка задачи называла baseline «3 файла (`limits.js`, `subscription.js`,
`tripAddons.js`)» — это ЗАМЕР ДРУГОГО ДЕРЕВА, до TRIP-388. Сегодня 9: те три
плюс `design/Layout.jsx`, `CalendarLens`, `DocsLens`, `EditLens`,
`ScreenAccount`, `SettingsLens`.

## Предикат повторяет TS, и это проверено ПРОБОЙ, а не чтением исходников

Правило TS (`processCommentPragmas` → `getLeadingCommentRanges(text, 0)`,
`PragmaKindFlags.SingleLine`, «побеждает последняя директива») проверено
прогоном настоящего `tsc` 5.9.3 по файлу с заведомой ошибкой типов:

| написание | проверяется |
|---|---|
| `// @ts-check` первой строкой | да |
| `//@ts-check`, `/// @ts-check`, `//   @ts-check` | да |
| `// @ts-check` после блочного комментария и пустой строки | да |
| `// @ts-check и почему` (текст после) | да |
| `@ts-check` внутри БЛОЧНОГО комментария | **нет** |
| `// @ts-check` ниже первой строки кода | **нет** |
| `// TODO @ts-check` (не в начале комментария) | **нет** |
| `// @ts-check-foo` | **нет** |
| `// @ts-check`, ниже `// @ts-nocheck` | **нет** (последняя побеждает) |

★Эта таблица живёт не только в шапке гарда, но и ТЕСТОМ: пятнадцать написаний
прогоняются пинованным `tsc`, и множество файлов, на которые он ругнулся,
сверяется с множеством, которое насчитал гард. Без такого теста предикат —
правдоподобная догадка о чужой семантике (TRIP-388: «инструмент проверяется
мутацией РАНЬШЕ, чем на него ссылаются»). У теста есть **датчик слепоты**: если
`tsc` не ругнулся ни на что, сверка пустых множеств зелена по построению.

## Почему правил ДВА, и почему одного не хватает

ТЗ просило «число файлов не падает». Одной агрегатной сверки МАЛО: счёт держат
плоским, потеряв прагму на одном файле и поставив на другом, — регресс покрытия
закрывается новой работой и проходит молча (мутация «оставить только счёт» валит
9 тестов). Одного пофайлового тоже мало: файл может ИСЧЕЗНУТЬ с базового пути, и
тогда пофайловому правилу не о чем спрашивать (мутация «оставить только его» —
4 красных). Поэтому оба блокируют, и оба ПЕЧАТАЮТСЯ.

**Маркера-обхода нет намеренно**, как у 2q.

## ★★★ Ревью Codex: вердикт не должен зависеть от того, КАК GIT НАЗВАЛ ПРАВКУ

Два P2 на PR #743, и оба — про молчаливый обход. Первый важнее и он про
устройство, а не про частный случай.

**1. Прощение по флагу `D` — обход через порог сходства.** Первая редакция
вычитала удаление, беря классификацию из `git diff --name-status`. Но git
выдаёт `D`+`A` вместо `R`, как только сходство падает ниже порога (по умолчанию
**50%**), а значит переезд С ПЕРЕПИСЫВАНИЕМ и снятой прагмой читался как
«файл удалён» → прощался. Воспроизведено прогоном: гард **печатал `-1` и выходил
0** — число падало на глазах при зелёном вердикте, худшая из форм.

Лечение структурное: **вердикт больше не спрашивает у git, что это было.** Два
правила, оба блокируют:
* **A (пофайловое, «на месте»)** — путь из базового набора, существующий на
  HEAD, обязан остаться в наборе. Ловит подмену «сняли с одного, поставили на
  другой», которую счёт не видит.
* **B (счётное, «исчезло с базового пути»)** — переезд, переезд с
  переписыванием и удаление судятся ОДНИМ вопросом: восполнено ли число (новый
  путь под прагмой). Переезд с живой прагмой = −1/+1 = ноль.

Связка `--find-renames=10% -l0` осталась, но ТОЛЬКО чтобы назвать преемника в
сообщении и применить к нему правило A; `-l0` — потому что git МОЛЧА бросает
поиск переименований на больших диффах. ⚠️Следствие, названное вслух: **удаление
файла из набора теперь КРАСНОЕ**. Прощать его нечем — «удалено» и «переехало с
переписыванием» по дереву неразличимы, а прощение первого есть готовый обход для
второго; цена в том, что снос экрана с прагмой требует разговора (сообщение так
и говорит).

★★★ЧЕМУ ЭТА ПОЧИНКА УЧИТ ОТДЕЛЬНО: **дверь прощения закрывают ВЕЗДЕ, а не в
одном месте.** Разделив правила, я оставил связке git ровно один прощающий вход
— вычет «переезд в TypeScript», — и он немедленно воспроизвёл тот же обход с
другой стороны: при пороге 10% git спаривает СНОС с ПОСТОРОННИМ новым `.ts`
(замерено, `R043`), гард печатал `-1`, объявлял чужой файл преемником и выходил
0. Лечение — признавать конверсию **ПО ПУТИ** (`x.js` → `x.ts`), без участия
git; конверсия ВМЕСТЕ с переездом под вычет не попадает намеренно. Инвариант
стал выразимым одной строкой: **связка может только УЖЕСТОЧАТЬ** и не прощает
нигде. Нашёл `code-simplifier` (восьмой заход подряд) — он же нашёл РЕГРЕССИЮ,
внесённую самой починкой ревьюера: разделение на A/B забрало пофайловое
следование за переименованием, и `git mv` + снятие прагмы + любая новая работа
снова давали зелёный.

⚠️Побочно: правило A по преемнику стало советовать «верни `// @ts-check`» файлу
`.ts`, где прагма не нужна и ничего не включает, — ложная инструкция посылает
следующего чинить не то. Запинено ассертом; мутация «снять фильтр по
расширению» валит ровно его.

★Порядок правил тоже оказался дефектом: сперва B стояло раньше A и перехватывало
вердикт (счёт падает и от потери на месте), печатая ПУСТОЙ список вместо имени
файла. Нехватка считается только по исчезнувшим, а печатаются ОБА диагноза —
ранний `exit` послал бы автора чинить половину.

**2. Терминаторы строк JS — их четыре, а искался один.** Конец однострочного
комментария определялся поиском `\n`, поэтому
`// @ts-check⟨U+2028⟩// @ts-nocheck` склеивался в ОДИН комментарий: tsc проверку
ВЫКЛЮЧАЕТ, гард считал файл покрытым. Отказ в опасную сторону. Замер на живом
tsc подтвердил все три (`CR`, `U+2028`, `U+2029`), а плоский пробел
(`// @ts-check // @ts-nocheck`) — НЕ терминатор, и tsc такой файл проверяет:
предикат с ним согласен, то есть чинить надо было ровно терминаторы.

⚠️И тут же личные грабли, записанные в этом же файле про NUL: **литеральный
U+2028 в исходнике завершает строку** — вписав его в регулярку, я сломал сам
гард (`node --check` упал), а в СТРОКОВОМ литерале теста он легален с ES2019 и
прошёл молча, оставив комментарий «символы записаны экранированно» ЛОЖЬЮ.
Управляющий символ пишется ИМЕНЕМ (`U+2028`), и проверяется это счётчиком по
файлу, а не глазами.

★Мутации по обеим починкам (19 применившихся, 0 зелёных): конец комментария
только по `\n` → 1 · вернуть прощение исчезнувшего → 4 · компенсация «на
единицу щедрее» → 4 · порог связки обратно 50% → 1 · правило A выключено → 9 ·
ранний `exit` в B → 1 · переезд в `.ts` не вычитается → 2. ⚠️Две из них
(порог и ранний `exit`) в первый заход вышли ЗЕЛЁНЫМИ — поведение не было
запинено ничем; фикстура под порог ОТКАЛИБРОВАНА замером (8 сохранённых строк
из 12 = `R028`: связывается на 10%, не связывается на 50%), а не подобрана на
глаз. И шесть якорей прежнего мутационного скрипта после переписывания
УСТАРЕЛИ и печатали «не применилась» — их пришлось пере-анкерить, иначе отчёт
был бы на шесть пунктов щедрее правды.

## ★★ Мутационный проход: что ломал и что покраснело

12 мутаций, каждая ПРИМЕНИЛАСЬ (скрипт проверяет отдельно — мутация, которая не
запустилась, не «поймана»), и одиннадцать поймались сразу:

блочный комментарий = прагма → 2 красных · предикат = текстовый греп → 5 ·
`@ts-nocheck` игнорируется → 2 · нет `process.chdir` в корень → 1 · ноль файлов
печатает OK → 1 · недостижимая база = пропуск → 1 · пофайловое правило заменено
агрегатом → 2 · удаление считается потерей → 1 · `.d.ts` попадает в набор → 1 ·
имя директивы читается подстрокой → 2 · ДАННЫЕ: снята живая прагма с
`src/lib/limits.js` → 1 (мутировать надо и данные, урок 2q).

★**Двенадцатая — «не учитывать переименования» — вышла ЗЕЛЁНОЙ**, то есть
обработка renames не была запинена ничем. Причина структурная и стоит того,
чтобы её знать: у переименованного файла старый путь не существует, и потеря
прагмы читается как «файл удалён», то есть **прощается**. Тест «переезд файла с
прагмой → зелёный» этого не ловит ПО ПОСТРОЕНИЮ — оба поведения зелены. Ловит
только «переезд СО СНЯТОЙ прагмой → красный», он и дописан. Практический вывод:
`git mv` + снятие прагмы в одном PR было бы отмыванием регресса.

## ★★★ Пять дефектов нашёл `code-simplifier`, и все — прогоном, а не чтением

Седьмой заход подряд, когда он находит то, чего не нашли ни тесты, ни ревью.
Общее у всех пяти: **тесты покрывали случаи, где предикат и tsc СОГЛАСНЫ**, а
жили дефекты ровно там, где стороны расходятся — тот же узор, что «проверено
одно из двух заявленных поведений» в TRIP-388.

1. **ТИХИЙ ЗЕЛЁНЫЙ на не-ASCII пути.** `git grep -l` и `git diff --name-status`
   печатают такие пути C-квотированными (`"src/\303\274ber.js"`), фильтр
   расширений спотыкается о завершающую кавычку, и файл выпадает из наблюдения
   ЦЕЛИКОМ: `src/über.js` со снятой прагмой давал `1 → 1 (+0)` и **exit 0**.
   Лечение — `-c core.quotePath=false` в обёртке `git()`; обе стороны сверки
   ходят через неё, поэтому чинится одним местом.
2. **Предикат расходился с tsc в ПЯТИ написаниях, и все — НЕДОУЧЁТ**: BOM
   U+FEFF, NBSP U+00A0, NEL U+0085 перед прагмой, шебанг строкой выше и другой
   регистр (`// @TS-Check` — TS сравнивает имя директивы без учёта регистра).
   Цена не тихая: **BOM, дописанный редактором в шапку файла с ЖИВОЙ прагмой,
   выкидывал бы файл из набора и гард краснел бы «верни прагму» — про прагму,
   которая на месте и работает.** Это класс «маркер, вынуждающий лгать».
   ⚠️Починка регистра в предикате БЕЗ `-i` у `git grep` была бы ИНЕРТНОЙ:
   кандидат просто не находится. Одно правило — два места.
3. **Переезд `.js → .ts` давал ЛОЖНЫЙ КРАСНЫЙ** (`-1`, exit 1, «файл потерял
   прагму»), хотя у `.ts` прагма не нужна и покрытие ВЫРОСЛО — то есть гард был
   красен на ходе, ради которого эпик и заведён. Вычитается и печатается.
4. `!renamed.has(p)` в списке «добавленных» — мёртвая клауза: карта ключуется
   СТАРЫМ путём, а фильтруется НОВЫЙ. Переезд отчитывался как новое покрытие
   (число верное, врёт строка).
5. `export function tsCheckEnabled` — ложная афиша: модуль на верхнем уровне
   зовёт `process.exit`, поэтому импорт экспорта УБИВАЕТ процесс импортёра.
   Экспорт снят (тесты гоняют гард подпроцессом).

★Все пять запинены тестами, и каждый тест увиден красным мутацией: снять
`core.quotePath` → 1 · вернуть узкий список пробелов → 1 · убрать ветку шебанга
→ 1 · сравнивать регистр → 1 · убрать `-i` у `git grep` → 1 · считать переезд в
`.ts` потерей → 1 · вернуть сверку по ключам `renamed` → 1. Пять расходящихся
написаний добавлены В ТУ ЖЕ фикстуру, которую судит настоящий `tsc` (15 форм) —
не отдельным ассертом с моим представлением о TS.

⚠️Осознанно НЕ правил (решение отложено, названо вслух): база читается по
`BASE_REF`, а переименования — трёхточечным `BASE_REF...HEAD`; если `dev` после
точки ветвления ПОСТАВИЛ прагму в файл, которого ветка не трогала, гард обвинит
автора. Это **домашняя конвенция всех соседей** (2l, 2m устроены так же), а в CI
`actions/checkout` даёт merge-коммит, где расхождения нет. Менять — всем гардам
разом и отдельным решением.

## ⚠️ Ловушка замера, которая не просто врёт, а ПИШЕТ В ДЕРЕВО

ТЗ предупреждало: мерить только пинованным `node_modules/.bin/tsc` (`npx tsc`
утащит другую мажорную версию → `TS5101`) и только конфигом `jsconfig.json` (под
другим именем теряется подразумеваемый `allowJs` → `TS18003 «no inputs»`, что
выглядит как «нечего проверять»). **Незаписанным было третье, и я в него
влетел:** вместе с `allowJs` теряется подразумеваемый **`noEmit`**, поэтому
прогон `tsc -p ./jsconfig.checkjs.tmp.json` не только мерит не то — он
**ЭМИТИТ `.js` рядом с каждым `.jsx`**. В рабочее дерево легло 117 файлов
(`src/pages/DocsLens.js` рядом с `DocsLens.jsx`), и остановился он только на
`TS5055 «would overwrite input file»` — то есть на первом `.js`-ИСХОДНИКЕ, а все
`.jsx` к тому моменту были перезаписаны. Заметно это стало по `git status`, а не
по выводу tsc. Правило: мерить `--checkJs` **флагами поверх настоящего
`jsconfig.json`**, а не копией конфига под другим именем.

## Цена `checkJs: true` — замер, и он зависит от периметра

Пинованный tsc 5.9.3, `-p ./jsconfig.json --checkJs --noEmit`, 2026-08-09:

* периметр `jsconfig` (214 файлов программы) — **420 ошибок в 155 файлах**;
* всё `src/` (include `src/**`, exclude только `node_modules`/`dist`) — **401 в 147**.

Оба числа названы намеренно: «сколько стоит включить checkJs» без периметра не
определено, и подставить одно вместо другого легко. Число из ТЗ (**1366**) —
замер дерева ДО TRIP-388, где 21 компонент ДС получил аннотации и снял сотни
TS2739/TS2741 (см. [[triplanio-ci-guard-is-code]], «запечатанный набор пропов —
свойство деструктуризации»). Записано в шапке гарда, чтобы следующий не мерил в
четвёртый раз.

## Границы, названные вслух

* Прагма на файле, который tsc НЕ ЗАГРУЖАЕТ, инертна (программа = `include` +
  граф импортов). Гард этого не проверяет: нужен прогон tsc, а джоба `guards`
  намеренно без `npm ci`. Замер на вводящем PR: все 9 файлов в программе.
